# easy-ja：わかりやすい日本語のチェック

アプリやウェブサイトの日本語を、知的障害のある人、日本語を学んでいる外国人、高齢者、子どもにも伝わる文章にする。基準は厚生労働省「[わかりやすい情報提供に関するガイドライン](https://www.mhlw.go.jp/seisakunitsuite/bunya/hukushi_kaigo/shougaishahukushi/dl/171020-01.pdf)」（以下、ガイドライン）。

## コマンドの実行方法

`npx @ter4uchi/easy-ja` で実行する。

調べる範囲をユーザーが示していなければ、変更したファイルや、話題になっている画面のファイルを指定する。

## 1. 機械的なチェック

```sh
npx @ter4uchi/easy-ja --format json <ファイルやディレクトリ>
```

`error` があると終了コード `1` で終わるが、コマンドの失敗ではないので、そのまま JSON を読む。

- `error` は直す。`warning` は文脈を見て、直すかどうかを判断する
- `suggestion` は一例なので、前後の文に合うものを選ぶ
- 設定ファイル（`.easyjarc.json`・`easy-ja.config.json`・`package.json` の `easyJa`）の `allow` にあることばは、その場面でいつも使う決まったことば（常とう語）なので、言いかえない

## 2. 文脈のチェック

```sh
npx @ter4uchi/easy-ja --format segments <ファイルやディレクトリ>
```

日本語を含む文字列が、ファイル・位置・種類（`kind`）つきで一覧になる。`{…}` は、実行時に名前や数などが入る部分や、コード・URL など文章ではない部分。

`string`・`template` には、ログやエラーの種類を表す文字列など、画面に出ないものもまざる。画面に出る文字列かどうかは、`kind` とまわりのコードを見て判断し、画面に出ないものは調べなくてよい。

この一覧を読み、次の観点で問題を探す。1つのファイルの文字列はまとめて読み、文字列どうしの関係（表記のゆれ、話の順番）も見る。

- **比喩・暗喩・擬人法**（ガイドライン p.3）：「白黒つける」「空気が読めない」「鬼のような」「壁が立ちはだかる」など、文字どおりに読むと意味を取りちがえる表現
- **主語の省略**（p.5）：誰が・何がするのかが書かれておらず、取りちがえるおそれのある文。例：「返却日を２週間延ばすことができます」→「本を借りた人は、返却日を２週間延ばすことができます」。ボタン名・見出し・項目名のような短いラベルや、画面を見ている本人への指示で、行う人が明らかなものは対象外
- **抽象的な説明**（p.2）：定義や抽象的なことばだけで、読み手に何が起きるのか・何をすればよいのかが伝わらない文。具体的な場面や行動に書きかえる
- **必要度の低い情報**（p.3）：読み手にとって重要度の低い補足・例外・細かい条件。削るか、窓口で聞いてもらうなど別の方法に分ける
- **話や手順の順番**（p.4）：起きる順番と書いた順番が逆になっている文章や、いくつもの手順を1つの文に詰めこんだもの。手順は番号つきの箇条書きにする
- **表記のゆれ**（p.3）：同じものを、場所によって違う名前や書き方で呼んでいるもの（「図書カード」と「図書館カード」、「ログイン」と「サインイン」など）。どちらに揃えるかを示す
- **年齢に合わないことば**（p.8）：大人向けの文章なのに、子どもに話しかけるような表現（「〜しようね」「よくできました」など）

指摘するのは、読み手が誤解したり、何をすればよいかわからなくなったりするおそれがはっきりあるものだけにする。1 の機械的なチェックと同じこと（文の長さ、漢字、難しいことば、二重否定など）は、ここでは繰り返さない。

## 3. 報告する・直す

機械的なチェックと文脈のチェックは、分けて報告する。

直すように頼まれたときは、次のことを守る。

- 文字列の中身だけを変える。変数名・翻訳キー・`${name}` や `{count}` などの埋め込み部分は変えない
- 同じ文言が翻訳ファイルなど複数の場所にあれば、すべて揃える
- 文を分けると画面に収まらなくなるなど、見た目に関わる判断が必要なときは、ユーザーに確認する
- 直したあと、1 のコマンドをもう一度実行し、`error` が残っていない（終了コードが `0` になる）ことを確かめる
